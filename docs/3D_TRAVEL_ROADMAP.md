# 여행 경로 안정화 및 3D 지형 재생 개발 계획

작성: 2026-09-15. 기준 소스: `9bcfb4fd81281f54d85cfb1173897d391508c59e`.

이 문서는 사용자와 논의한 방향을 구현 계획으로 정리한 것이다. 원본 저장소 검토 당시의 계획이며, 새 3D 프로젝트의 현재 구현·검증 상태는 `IMPLEMENTATION_STATUS.md`에서 관리한다. 소요 시간과 성능 수치는 실측 결과가 아니라 작업 순서·목표이며, 시제품 측정 후 범위를 확정한다.

## 1. 목표

일반적인 Android 스마트폰에서 긴 영상 사전 생성 없이 여행을 실시간 3D로 재생한다. 산악·캐년에서는 큰 지형 형태와 차량의 오르내림을 보여주고, 장거리 비행에서는 지구 곡률과 항로를 보여준다. 사진·음악·기존 다이어리·MP4 기능을 유지한다.

우선 해결할 사용자 문제는 타임라인 경로가 두 줄로 보이거나 이동이 어색한 현상이다. 수평 경로를 신뢰할 수 있게 만든 뒤 고도와 3D 연출을 붙인다.

첫 버전 범위:

- 간략한 실제 지형, 단순한 3D 자동차/비행기, 지형과 진행 방향을 따르는 카메라.
- 기기에 미리 준비된 지역 지형 팩을 이용한 오프라인 재생.
- 표준 30fps 목표, 기기 성능에 따라 지형 상세도와 내부 렌더링 해상도 조절.
- 기존 2D 표시를 비교·호환용으로 유지하고 단계적으로 3D를 활성화.

첫 버전 이후로 미룰 범위:

- 실제 건물·사진 수준의 도시·위성사진·세밀한 바위 표면.
- 전 세계 고해상도 지형을 앱 설치 파일에 포함하는 방식.
- 전 세계 도로망을 이용한 자동 경로 복원. 필요한 사례와 데이터 비용을 확인한 후 별도 결정.

## 2. 확인된 사실과 미확정 원인

사용자가 말한 두 줄 현상의 실제 화면/데이터는 아직 받지 않았다. 아래는 코드에서 확인한 동작이며 원인 확정은 재현 후에 한다.

- `MovementTimelineCanonicalizer`는 시간 중복을 해결하지만 실제 왕복·시간이 어긋난 중복·표시용 연결선까지 동일한 문제로 다루지는 않는다.
- `TravelMapRenderer`는 현재·과거·미래의 경로를 함께 표시한다.
- renderer가 500m/15분 이내 공백에 표시용 직선 연결선을 추가한다. 지형이나 도로 연결성을 확인하는 조건은 없다.
- renderer에서만 경로 끝점을 30m 이내 방문지에 맞추는 보정이 존재한다. 타임라인이 사용하는 좌표와 달라질 여지가 있다.
- 좌표 모델과 파서에는 고도 필드가 있다. 그러나 Room에서 구간 시작·끝 좌표를 별도 컬럼으로 저장/복원할 때 고도를 보존하지 않으며, 구간의 시간별 `rawPoints`도 현재 저장하지 않는다. `polylineJson`에 포함된 고도는 남을 수 있으므로 고도가 전부 유실된다고 단정하지 않는다.
- 현재 지도 데이터에는 지형 고도 격자가 없다. 새 데이터 공급 방식이 필요하다.
- 기존 JVM 테스트 277개 통과는 기준선이다. 사용자 사례, 실제 3D 성능, 실제 MP4 품질의 검증을 대신하지 않는다.

## 3. 단계별 실행 계획

### 단계 0 — 재현 사례와 기준선 확보

작업:

- 사용자에게 두 줄 현상의 캡처/짧은 녹화, 날짜와 구간을 받아 현상을 분류한다. 필요한 경우 해당 범위의 Timeline JSON을 로컬에서 분석한다.
- 원본 입력을 유지하고 파싱 결과, 정리된 구간, 표시용 연결선, 재생 위치를 비교할 개발용 진단 출력을 만든다.
- 실제 데이터가 도착하기 전에는 합성 사례로 중복, 왕복, 평행 도로, 시각이 조금 어긋난 기록, 방문지 연결, 관측 공백을 검증한다.
- 같은 테스트 여행으로 재가져오기/저장 후 열기, 준비 시간, 메모리, 재생 상태를 기록한다.

완료 기준:

- 합성 재현 테스트가 있고, 실제 사례를 받았으면 문제가 생기는 두 선의 출처·시간·구간 ID를 식별한다.
- 실제 사례가 없으면 사용자 문제 해결 완료로 보고하지 않는다.

### 단계 1 — 경로 데이터와 저장 구조 통일

작업:

- 하나의 공통 경로 준비 단계에서 관측 경로, 신뢰도, 고도, 추정 여부, 명시적 공백을 구성한다. 지도 선·차량 위치·카메라·MP4가 이를 공유한다.
- 시간 중복과 공간 유사성을 함께 보고 같은 이동의 중복만 제거한다. 실제 왕복·헤어핀·다른 날 재방문은 보존한다.
- 방문지 연결은 거리뿐 아니라 시간과 해당 구간의 관계를 확인한다. renderer 내부에서 원본과 다른 경로를 임의로 만들지 않도록 옮긴다.
- 거리가 가깝다는 이유만으로 지름길을 만들지 않는다. 짧고 근거가 충분한 구간만 추정 연결하며, 나머지는 명시적인 공백으로 유지한다.
- 전체 보기에서는 실제 모든 경로를 볼 수 있게 하되, 재생에서는 현재 구간과 최근 이동을 중심으로 표현한다. 데이터 삭제와 시각적 강조를 구분한다.
- 재처리에 필요한 시간별 지점, 고도, 출처/신뢰도를 제한된 크기의 로컬 형식으로 저장한다. 원본 전체를 무조건 DB에 복제하지 않는다.
- Room 마이그레이션으로 기존 여행·사진 연결·수동 수정 내용을 보존한다. 기존 여행에 없는 원본 지점이나 고도는 추정값/미상으로 구분하고 재가져오기 전까지 관측값으로 취급하지 않는다.

주요 파일:

`GoogleTimelineJsonParser.kt`, `MovementTimelineCanonicalizer.kt`, `TripRepositoryImpl.kt`, `TravelerDatabase.kt`, `Entities.kt`, `TravelStoryTimeline.kt`, `TravelMapRenderer.kt`.

완료 기준:

- 같은 재생 시점에 화면 선과 차량이 같은 경로를 참조한다. MP4는 타이틀/엔드 카드 오프셋을 제외한 같은 본편 시점으로 비교한다.
- 중복은 제거되며 실제 왕복/헤어핀은 남고, 근거 없는 직선 연결은 생성되지 않는다.
- 저장 직후와 앱 재시작 후 경로·고도·사진 연결이 유지된다.

### 단계 2 — 지역 지형 팩과 고도 보정

작업:

- 첫 대상은 실제 산악/캐년 여행 한 구간으로 제한한다. 공개 DEM 후보의 범위·결측·수직 기준·재배포 조건을 확인하고 하나를 선정한다.
- 개발 환경에서 높이 격자를 타일과 여러 상세도로 미리 가공한다. 스마트폰에서 원본 대용량 GIS 자료를 매번 변환하지 않는다.
- 지형 팩에 범위, 좌표계, 고도 기준, 데이터 버전, 출처, 무결성 정보를 포함한다.
- 1차 배포 방식은 파일 선택으로 지역 팩을 가져오는 방식으로 가정한다. 앱의 네트워크 권한을 추가하지 않는다. 앱 내 자동 다운로드는 별도 제품 결정이다.
- 경로 주변에서 필요한 타일만 읽고 메모리 상한이 있는 캐시를 사용한다. 범위를 벗어나거나 팩이 없으면 기존 지도 표현과 고도 미상 처리를 사용한다.
- GPS 고도와 DEM 고도를 섞기 전에 수직 기준 차이를 처리한다. 불명확한 경우 신뢰 가능한 한 출처를 우선 사용하고 출처를 남긴다.
- 위치 정확도·앞뒤 진행·원래 관측 시간·경사 변화·주변 지형을 함께 이용해 고도 급락/급등을 탐지한다. 재생 배속을 실제 속도 판정에 쓰지 않는다.
- 한 점만 튀는 경우와 여러 점에 걸친 실제 오르막을 구분한다. 헤어핀·정상·계곡의 실제 형태를 지우는 과도한 평활화는 피한다.
- 절벽 가장자리에서 근거 없이 좌표를 낮은 쪽/높은 쪽으로 옮기지 않는다. 다리·터널·긴 결측은 DEM만으로 해결됐다고 판단하지 않으며, 불확실 구간으로 유지한다.

완료 기준:

- 정상 오르막/내리막은 보존하고, 주입한 단일 고도 오류는 검출한다.
- 캐년 가장자리 오차·다리·터널·결측·팩 범위 밖 사례에서 갑작스러운 추락이나 가짜 확정 경로를 만들지 않는다.
- 지형 준비 결과를 저장해 다음 재생에서 재사용한다.

### 단계 3 — 지역 3D 주행 시제품과 성능 판단

작업:

- 기존 Kotlin 앱 내부의 GPU 렌더러로 간단한 지형 격자, 경로, 자동차, 색상·명암을 그린다. 우선 검토안은 OpenGL ES이며 최소 기기의 기능 확인 후 구체 버전을 결정한다.
- 가까운 지형만 자세히 그리는 방식과 화면 밖 지형 제외, 타일 경계 이음 처리를 구현한다.
- 자동차 위치와 기울기는 보정된 경로와 고도에서 구한다. 표현용 기울기를 완화해도 데이터 자체는 변경하지 않는다.
- 카메라는 진행 방향과 지형을 미리 보며 완만하게 따라간다. 급회전·정차·역방향 탐색에서도 튀지 않고 지형 아래로 들어가지 않도록 한다.
- 지형과 사진을 준비하는 작업을 UI 스레드 밖에서 수행하고, 사진/지형 캐시 상한을 둔다.
- 먼저 사용자가 가진 기기와 비교용 중급 실기기에서 측정한다. 에뮬레이터 결과로 일반 스마트폰 성능을 확정하지 않는다.

완료 기준과 판단:

- 산악/캐년 구간의 상승·하강이 주변 지형과 함께 눈에 보인다.
- 기준 중급 기기에서 30fps를 목표로 프레임 시간 중앙값/p95, 끊김, CPU/GPU 부하와 발열을 기록한다. 평균 fps만 보고 통과시키지 않는다.
- 캐시가 준비된 기준 여행은 재생 시작 3초 이내를 초기 목표로 삼는다. 기기·데이터 크기와 함께 보고하고 실측 후 조정한다.
- 10분 연속 재생 및 반복 탐색에서 메모리가 계속 증가하지 않고, OOM/ANR이 없어야 한다.
- 목표를 못 맞추면 지형 상세도·내부 해상도·연출 복잡도를 먼저 줄인다. 이 판단 전에 전 세계 범위로 확장하지 않는다.

### 단계 4 — 지구본·비행·사진 연출 통합

작업:

- 지역 주행이 검증된 뒤 지구본과 지역 지형 사이 전환을 구현한다. 날짜변경선, 장거리 좌표 정밀도, 좌표계 전환에서의 튐을 별도로 다룬다.
- 비행은 실제 기록/추정 항로를 구분하고, 고도가 없는 비행의 표현용 높이를 실제 측정 고도로 표시하지 않는다.
- 방문지 도착 시 감속·짧은 카메라 회전·사진 표시를 기존 대표 사진 시간표와 결합한다.
- 카메라 상태는 재생 시간으로 재현할 수 있게 구성하여 탐색/되감기/반복/영상 출력이 서로 달라지지 않게 한다.
- 과도한 회전과 흔들림을 줄이는 카메라 옵션을 제공한다.

완료 기준:

- 자동차→방문지→비행→다음 지역 전환에서 공간적 튐과 사진 순서 회귀가 없다.
- 날짜변경선 통과, 정지/재개, 배속, 되감기와 반복 재생이 일관된다.

### 단계 5 — 3D MP4와 안정화

작업:

- 동일한 장면/카메라 평가 결과를 앱 화면과 MediaCodec 입력 surface에서 렌더링한다. 현재 매 프레임 Canvas bitmap 업로드를 하는 경로는 직접 GPU 출력으로 교체한다.
- 1080p/30fps를 표준 출력 목표로 검증하고, 기기/코덱 제약 시 720p/30fps 대안을 제공한다. 모든 기기에서 동일 속도를 보장하지 않는다.
- WAV 전체의 반복 복사를 줄이고 사진 bitmap 캐시에 상한을 둔다. 지형 데이터가 TimeShape와 함께 불필요하게 상주하지 않도록 수명을 분리한다.
- 제작/저장 예외, 취소, 화면 회전·백그라운드 전환, 저장 공간 부족, 코덱 실패와 임시 파일 정리를 검증한다.
- 주소 보호 옵션을 실제 출력에 적용하고, 대표 사진 재가져오기 복원과 구형 Android 갤러리 저장 누락을 함께 수정한다.

완료 기준:

- 같은 본편 시점의 차량 위치·경로·카메라·사진이 화면과 영상에서 일치한다.
- 영상/오디오 길이와 동기, 출력 파일 재생, 취소와 실패 정리가 통과한다.
- 기준 영상의 길이 대비 내보내기 시간, 최고 메모리, 발열을 실제 기기별로 보고한다. 현재 단계에서 내보내기 속도를 약속하지 않는다.
- 기존 회귀 테스트 및 추가 회귀 테스트, lint, Room 마이그레이션, 실제 기기 테스트를 완료한다.

| 지형 팩·고도 보정 | 중간~높음 | 공통 경로 구조 | 산악 구간 높이와 오류 진단 |
| 지역 3D·차량·카메라 | 높음 | 지역 지형과 공통 경로 | 스마트폰에서 재생되는 시제품 |
| 지구본·지역 전환 | 높음 | 지역 시제품의 성능 통과 | 비행/주행을 잇는 여행 재생 |
| 영상 출력·기기별 안정화 | 중간~높음 | 공통 3D 장면 | 재생 가능한 MP4와 성능 결과 |

가장 큰 구현 비용은 3D 렌더러 및 두 좌표 규모의 전환, 가장 큰 데이터 위험은 실제 경로 공백과 절벽 주변 고도 오류다. 현재는 일수 단위의 확정 일정을 제시하기 어렵다. 첫 지역 시제품까지의 결과를 보고 잔여 일정과 지원 기기 범위를 산정한다.

경로 안정화 완료 후 지역 3D 시제품을 중간 점검 대상으로 삼는다. 이후 지구본과 제품 통합으로 확장한다. 특정 기술이 이미 확정된 것처럼 전체 앱을 한 번에 교체하지 않는다.

## 5. 사용자 정보와 기본 가정

- 있으면 필요한 정보: 두 줄 현상 캡처/녹화와 날짜·구간, 실제 사용하는 스마트폰 모델, 첫 지형 시제품에 사용할 산악/캐년 여행.
- 위 정보가 없어도 코드 구조 정리 계획과 합성 테스트 준비는 가능하다. 실제 사용자 현상 해결 및 기기 성능 완료 판정은 자료 확보 후에 한다.
- 기본 가정: Android·로컬 처리 유지, 지형 팩 사전 가져오기, 30fps 목표, 단순한 모델과 지형, 기존 여행과 수동 수정 보존.
- 온라인 자동 다운로드, 전 세계 도로 맵 매칭, 위성사진은 이번 기본 범위에 넣지 않는다.

## 6. 참고 근거

- [Android OpenGL ES](https://developer.android.com/develop/ui/views/graphics/opengl/about-opengl): Android GPU 렌더링과 기기별 지원 확인.
- [MediaCodec](https://developer.android.com/reference/android/media/MediaCodec): GPU에서 encoder input surface로 출력하는 경로.
- [USGS SRTM](https://www.usgs.gov/centers/eros/science/usgs-eros-archive-digital-elevation-shuttle-radar-topography-mission-srtm): 공개 높이 데이터 후보. 약 30m 수평 간격을 도로 높이의 정확도 보장으로 해석하지 않는다.
- [Copernicus DEM](https://dataspace.copernicus.eu/explore-data/data-collections/copernicus-contributing-missions/collections-description/COP-DEM): 지표면 모델은 수목·구조물 영향을 포함할 수 있음을 고려한다.
- [Map matching 연구](https://www.microsoft.com/en-us/research/publication/hidden-markov-map-matching-noise-sparseness/): 도로망·시간 흐름을 활용한 별도 고도화 후보. 현재 중복 제거 알고리즘이 이미 도로 맵 매칭을 한다는 뜻은 아니다.
